## Clinic schema after alterations

[clinic.sql](clinic.sql) first recreates `clinic_db`, creates three tables, and inserts 4 patients, 3 doctors, and 4 appointments. Its final `ALTER TABLE` statements change the schema as follows:

| Table | Final change |
| --- | --- |
| `patients` | Adds nullable `phone VARCHAR(100)` and renames `city` to `patient_city`. |
| `doctors` | Adds nullable `email VARCHAR(100)`. |
| `appointments` | Expands `status` from `VARCHAR(30)` to `VARCHAR(150)`. |

The inserted rows have no phone or email values, so those new columns remain `NULL`. Any follow-up query for a patient's city must use `patient_city`. The script contains no `SELECT` statement to display its sample rows.

| --- | --- |

The query orders counts from largest to smallest. The two courses with a count of `2` can appear in either order because no secondary sort is specified. ## Blog authors and posts

[blog.sql](blog.sql) declares an author table named `auto` and a `post` table. Both use auto-incrementing primary keys; the inserts omit those key columns so IDs are generated by the database.

The sample inserts expect the following author IDs in a newly created database with the default auto-increment settings:

| Author | Expected autor_id | Posts referring to that ID |
| --- | --- | --- |
| Omar | 1 | 2 |
| Ahmed | 2 | 1 |

Each post requires a non-null `autor_id` referencing `auto.autor_id`, so one author can have multiple posts. The script creates and populates the tables but includes no `SELECT` query to display them. These notes are based on source inspection; the script has not been executed against MySQL.

## Fitness studio relationships

[fitness_studio.sql](fitness_studio.sql) declares four tables in the existing `Fitnessstudio` database:

| Relationship | Implementation |
| --- | --- |
| Member to training plan | Nullable `Mitglieder.id_trainingspläne` references `Trainingspläne.id`. |
| Training plan to exercises | `Trainingspläne2Übungen` links plans and exercises through two foreign keys. |

A member can have no plan or one assigned plan; multiple members can share the same plan. A plan can contain multiple exercises, and an exercise can belong to multiple plans. The junction table's composite primary key `(id_Trainingspläne, id_Übungen)` prevents duplicate plan/exercise pairs.

The script defines tables only, with no sample inserts or queries. Accented identifiers such as `Übungen` and `Trainingspläne` retain their source spelling.

## Vulnerability inventory query result

[vulnerability_inventory.sql](vulnerability_inventory.sql) inserts ten target systems, ten vulnerability records, and eight associations. Its final query is expected to return:

| betriebssystem | total |
| --- | --- |
| Windows 10 | 4 |
| CentOS 7 | 3 |

`COUNT(*)` counts association rows per operating-system name. The inner join omits systems without associations, and `HAVING total > 2` excludes the Windows Server 2019 group with one association. The composite key prevents duplicate system/vulnerability pairs; both foreign keys use `ON DELETE CASCADE` to remove associations when a referenced row is deleted.

These are results derived from exercise data, not findings from scanning real systems. MySQL execution has not been performed.

## App store sample data scope

[app_store_hub.sql](app_store_hub.sql) recreates `appStoreHub` and defines six tables: `users`, `developers`, `apps`, `downloads`, `reviews`, and `subscriptions`. Its supplied inserts populate only `users`, with 50 rows; the other five tables remain empty after a fresh run. The script includes no `SELECT` query to display the data.

Each app requires an existing developer. Downloads, reviews, and subscriptions each require existing user and app rows, so follow-up inserts must create developers and apps before those dependent records. The schema does not declare a unique `(user_id, app_id)` pair in those three tables; their separate primary keys allow repeated pairs.

These notes describe the supplied SQL source; the script has not been executed against MySQL.
